# ADR-0003 命令沙箱：交互默认 auto，沙箱外重跑只能由人批准

状态：已接受（2026-11-26，用户确认） · 实施：`docs/plans/active/PLAN-20261126-runtime-roadmap.md` 的安全阶段（P0 先做无人值守的预算上限，沙箱不在 P0）

## 背景

- 命令沙箱由 `PAICLI_COMMAND_SANDBOX=off|auto|required` 控制，默认 `off`。Linux 用 bubblewrap，macOS 用 Seatbelt（系统自带的沙箱机制）
- 沙箱里没有网络，也看不到 `~/.m2`、`~/.gitconfig`，所以 `mvn`、`npm install`、`git push` 会失败；macOS 的 Seatbelt 里 JVM 还有以 139 退出的已知问题
- 主要使用场景是自己日常写 Java 代码，`mvn test` 是最高频的命令
- auto 会话模式下，`execute_command` 先交给审查模型 `LlmApprovalClassifier` 判断
- 原路线文档要求：交互优先 `auto`，降级需要用户明确知情并授权；无人值守默认 `required`

## 决定

1. **交互命令行默认 `auto`。** 沙箱允许只读访问依赖缓存（`~/.m2`、`~/.gradle` 等，具体名单在实现时按平台确定），网络默认关闭
2. **沙箱外重跑只能由人批准，一次一批。** 命令在沙箱里失败，而且能判断是沙箱限制导致的（网络被拒、写权限被拒等），弹确认框问“是否在沙箱外重跑这一次”。用户批准才重跑，并写审计记录
3. **审查模型不能代批。** 审查模型、人工确认、沙箱三层各管各的，谁都不能替另一层做决定
4. **判断不出就不提示。** 失败原因不确定时按普通失败处理，不弹升级确认；宁可少提示，不能误放行
5. **无人值守永不升级。** `-p`、Runtime API、后台任务执行命令时沙箱为 `required`，沙箱不可用就拒绝执行
6. **被安全策略拒绝的操作照旧不能批准。** PathGuard、CommandGuard 在沙箱之前检查，升级只针对“沙箱本身的限制”，不绕过其他策略

## 放弃的方案

| 方案 | 为什么不选 |
|---|---|
| 保持默认 `off`，只在启动画面提示 | “安全由确定性代码执行”的原则落空 |
| 默认 `auto`，不提供升级 | 需要网络的常用命令直接失败，用户只能自己去改环境变量，最后多半整体关掉沙箱，反而更不安全 |
| 允许审查模型批准升级 | 审查模型只看用户原话和命令参数，看不到沙箱为什么拒绝；让它放行等于让模型自己解除限制 |
| 无人值守也允许按白名单升级 | 没人在场，“知情授权”无从谈起 |

## 后果

- 好处：大部分命令（读文件、grep、离线测试）在沙箱里完成，只有真需要网络或写权限时才由人显式放行；这是 Codex 公开的做法，行为可以讲清楚
- 代价：要分 Linux 和 macOS 两个平台实现和验证；“是不是沙箱导致的失败”要做启发式判断；第一次在新机器上用会多一些确认框
- 现有用 `serve --allow-command` 的场景，在没有沙箱的机器上会从“能执行”变成“拒绝”，需要在发布说明里写明
