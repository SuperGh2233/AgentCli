## 2. 当时的架构（对比时看这一节）

- **执行方式**：评测走无界面模式 `-p ... --permission-mode sandbox --output-format stream-json`，只用 ReAct；Plan / Team 不参与
- **内核**：`AgentLoop` 只负责“调模型 → 执行工具 → 写回对话”、取消、预算、事件；`createHooks()` 里按顺序直接 new 出模块：`LspDiagnosticsHook` → `ContextCompactionHook` → `ResourceFailureHook` → `SkillInjectionHook` → `RunawayReminderHook`（关掉的模块不创建）
- **五层上下文处理**（上下文预算 128k → 摘要阈值约 9.5 万 Token = 窗口 − 2 万输出预留 − 1.3 万缓冲）：
  1. 大结果落盘：单个工具结果超过 32,000 字符写进 `.haocli/tool-outputs/`，对话里只留头 2,000 + 尾 800 字符和读回提示
  2. 历史裁剪 `HistoryTrimmer`：上下文超过摘要阈值 × 0.4（约 3.8 万）触发，保留最近 6 条工具结果，超过 6,000 字符的旧结果裁成头 1,500 + 尾 500
  3. 局部折叠 `LocalFolder`：× 0.5（约 4.7 万），保留最近 2 条，短于 200 字符的不折
  4. 清理旧工具结果：× 0.6（约 5.7 万）
  5. 摘要压缩：达到摘要阈值
  - 模型报上下文超长时紧急压缩一次再重试；第 2–5 层的触发次数**没有对外输出**（只在容器里的日志），这一轮只能从单次输入骤降看出压缩发生过
- **重复调用提醒**：同类工具调用重复 3 次后提醒模型换思路
- **工具状态**：甲-1 已完成（`ToolStatus` 七种状态），只有 `read_file` 迁成独立 `Tool`，其余 17 个工具仍按文字前缀推断成败
- **模型调用重试**：最多 3 次、基础间隔 500ms；**所有 SSL 异常都不重试**（TLS 握手被对端断开时直接失败；`bb423ae` 已修）
- **结果 JSON**：有 `tools`、`harness_disabled`、`context_budget_tokens`；没有 `reason`、`context`（`bb423ae` 才加）
- **上限**：每次尝试最多 150 次模型请求、1000 万 Token、30 分钟（Hao CLI 自己的上限）；题目自己的 Agent 时限按 Terminal-Bench 2.0 默认（多数 900 秒）

### 两条路线的差别

| | DeepSeek 官方 | magpie → WorkBuddy |
|---|---|---|
| 每次模型请求耗时（中位数） | 8.7 秒 | 14.1 秒 |
| 做完的尝试需要的请求数（中位数） | 30 | 31 |
| 题目时限内没做完 | 3/37 | 16/53 |

模型行为接近（请求数几乎一样），但 magpie 每次请求慢约 60%，题目时限固定，所以超时明显变多。超时多主要是通道速度造成的，不是 Harness 变了。以后的优化对比必须两边都走 magpie。

### 补跑中发现的问题（后续优化候选）

- **regex-chess：单次输出太长撞上 600 秒请求上限**。这题让模型一次输出 6–9 万 Token；Hao CLI 的 OkHttp `callTimeout` 是 600 秒（整次请求的上限，`readTimeout` 300 秒管的是两次读之间的间隔）。DeepSeek 官方能在 600 秒内输出 6 万 Token（那次是部分完成），magpie 输出 8.5 万 / 6.2 万 Token 时两次都超时（`regex-chess__BwHcWDj`、`regex-chess__MxneHZg`），可以稳定复现，所以按失败计入、不再重跑。**2026-11-28 已修**：单次请求默认不再限制总时长（卡死仍由 300 秒读取间隔发现），见提交说明；还需要在 magpie 上重跑这题验证效果
- **large-scale-text-editing：Agent 进程被杀（137）**。题目是处理 100 万行 CSV，容器内存小，JVM 进程疑似被系统杀掉，没有输出结果行。候选改法：评测时给 JVM 设内存上限（比如 `-Xmx`），或者在适配器里记录退出原因
- 这两个问题和第 2 节记录的“TLS 握手断开不重试”（`bb423ae` 已修）一起，作为下一轮优化的对照项
